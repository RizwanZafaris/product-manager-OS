# Rendering this repository

Every file in Product Manager OS is plain Markdown. Layer files (templates, frameworks, knowledge, skills, agents, and os) carry a YAML frontmatter block with `layer`, `stage`, `gate`, `feeds`, `method` and `aliases`; SKILL.md files carry `name` and `description`, with those keys in a SKILL.graph.yml beside them. Links are relative Markdown links, checked by [../lint.py](../lint.py). The stage hub notes in os/maps/ (and docs/ARCHITECTURE.md, templates/architecture/system-design.md) also carry wikilinks, which lint.py checks against paths and aliases. Several files contain Mermaid code blocks, for example [templates/architecture/sequence-diagram.md](../templates/architecture/sequence-diagram.md) and [GRAPH.md](GRAPH.md). Mermaid blocks in templates render; the generated whole-tree graph in GRAPH.md is above Mermaid's default size limit and shows a size-exceeded notice on GitHub and in Obsidian, so read its tables instead.

This guide covers four ways to render the tree as a website or knowledge base.

## GitHub

Nothing to install. GitHub renders Markdown natively. Relative links work between files in the same repository. Mermaid diagrams render in file views and pull requests. YAML frontmatter appears as a small table at the top of a file. Clicking a link from one Markdown file to another stays inside GitHub's renderer. GitHub shows wikilinks as plain text; use the Markdown links beside them.

## Obsidian

1. Clone the repository, then open the repository folder as a vault in Obsidian.
2. Open **Settings**, then **Files and links**, and check two entries under it: **Use Wikilinks** should be off, so new links stay as relative Markdown links ([../lint.py](../lint.py) checks relative links); **New link format** should be **Relative path to file**, so a link Obsidian inserts is the same relative path lint.py and GitHub resolve. The repository's own [.obsidian/app.json](../.obsidian/app.json) already sets both (`useMarkdownLinks: true`, `newLinkFormat: "relative"`), so a vault opened straight from a clone of this repository needs no change here; check the two settings anyway if you use a different vault, reset your local config, or notice a new link land wrapped in double square brackets instead of as an ordinary parenthesized Markdown link.
3. Frontmatter appears as properties at the top of the note (or in the Properties view pane).
4. The graph view draws the Markdown links and wikilinks in note bodies. The `feeds` and `method` keys are plain paths, shown as text properties, not as edges; the rendering of those declarations is [GRAPH.md](GRAPH.md), generated by tools/graph.py. The `aliases` key is honoured, so [[Design Review Skill]]-style links resolve through it.

Obsidian is a document client, not a runtime client: it can read and edit the
files described above, with no connection to the local `pmos` runtime (phase
status, gate approval, the development handoff), and no validation of an edit
before it lands. For exactly which capability each client, including
Obsidian, GitHub, and a plain text editor, supports, see the capability matrix
in [COMPATIBILITY.md](COMPATIBILITY.md#the-capability-matrix); the Obsidian
control-station UI that would close this gap is deferred by the owner, not
built here.

**What is verified about the link settings above, and what is not (F18).** Two things are checked by commands in this repository, and a third is not. First, [../lint.py](../lint.py) `--os` resolves every relative Markdown link in the tracked tree against the files that exist, on every run, including the links in this file and in every template; that is a real, repeated check, not a one-time claim. Second, `python3 lint.py --json-syntax` parses every tracked `.json` file, [.obsidian/app.json](../.obsidian/app.json) included, and fails the build on a syntax error; `useMarkdownLinks: true` and `newLinkFormat: "relative"` were confirmed by direct inspection of the committed file, since no automated check here reads those two key values specifically, only that the file parses. Third, and not verified: whether Obsidian's own create, rename, and move commands keep a link's relative path correct under `useMarkdownLinks: true`, live, in the running application. No automation in this repository launches the desktop app, so that behavior is documented upstream by Obsidian and has not been independently exercised or recorded here. Say so plainly rather than implying a live test: a fresh-vault create, rename, and move across GitHub, Obsidian, and a built site (MkDocs or Quartz) is the acceptance this finding asks for, and only the link-resolution and JSON-syntax halves of it have run.

## MkDocs with Material

MkDocs refuses a `docs_dir` that contains `mkdocs.yml`, and pointing it at the whole repository would publish every Python and JSON file as a static asset, so keep a small site project whose build step copies the Markdown (and the non-Markdown files those pages link, such as LICENSE and lint.py) into its `docs` folder; put `site_dir` outside that folder. MkDocs needs a wikilink plugin (for example mkdocs-roamlinks-plugin) or the hub notes' wikilinks stay text.

Minimal `mkdocs.yml`:

```yaml
site_name: Product Manager OS
theme:
  name: material
markdown_extensions:
  - pymdownx.superfences:
      custom_fences:
        - name: mermaid
          class: mermaid
          format: !!python/name:pymdownx.superfences.fence_code_format
```

Install and build commands:

```bash
pip install mkdocs-material
mkdocs serve   # preview locally
mkdocs build   # generate site/ output
```

## Quartz

Point Quartz's content folder at a copy of the repository's Markdown, then build and serve it. Quartz keeps backlinks and a graph view, converting relative links to site paths automatically. The graph view uses the same link structure that Obsidian builds. Deploy the generated site to any static host.

Commands:

```bash
npx quartz create   # choose an existing folder
npx quartz build --serve
```

Set `markdownLinkResolution` to `"relative"` in `quartz.config.ts`.

## Guidance blocks in templates (F17)

Most templates teach through guidance comments, `<!-- like this -->`. Every renderer above hides an HTML comment in reading mode: GitHub, Obsidian reading view, MkDocs, and Quartz all render nothing where one sits. That is by design for the sentence about a template's own mechanics that nobody filling it in should have to read twice, but a 2026-09-12 audit measured templates/definition/prd.md at 3,111 whitespace-separated words with about 1,555 of them, roughly half, inside comments: a first-time reader in reading mode saw the fillable spine and the tables, not the teaching that explains them (finding F17).

templates/definition/prd.md is the pilot fix. Its guidance now sits in a collapsible block instead of a comment:

```markdown
<details open>
<summary>Guidance</summary>

The guidance text, as plain paragraphs and lists, blank-line separated so a
CommonMark renderer parses it as Markdown rather than as opaque HTML.

</details>
```

**Why `<details>`, and not the alternatives.** The two forms a reviewer would reach for first are an Obsidian callout (`> [!note]- Guidance`) and this one, and the choice was made by reading what each renderer above actually does with it, not by preference:

- **GitHub** renders `<details>`/`<summary>` as a native collapsible disclosure widget; it is a standard pattern in GitHub-flavored READMEs. An Obsidian callout is not GitHub's syntax: GitHub's own alert blocks are five fixed types (`[!NOTE]`, `[!TIP]`, `[!IMPORTANT]`, `[!WARNING]`, `[!CAUTION]`) with no fold suffix, so `[!note]-` fails that match and falls back to a plain blockquote whose first visible line is the literal, un-rendered text `[!note]- Guidance`, syntax noise a reader has to mentally discard.
- **Obsidian reading view** renders raw HTML in a note, `<details>` included, as the same native disclosure widget; this is documented Obsidian behavior, not a plugin. An Obsidian callout collapses here too, which is the one renderer it was designed for, but see the second bullet below for why that is not enough on its own.
- **MkDocs Material** (Python-Markdown) passes a block-level raw HTML element through to the built page unchanged, and a browser renders `<details>` as a native, clickable disclosure widget with no plugin and no JavaScript, purely from HTML5 semantics. Python-Markdown does not re-parse Markdown syntax inside a raw HTML block unless the page enables the `md_in_html` extension and the tag carries `markdown="1"`, which this repository's minimal `mkdocs.yml` above does not add, so the guidance text is written as plain prose and simple `-` lists that stay legible either way, rendered or literal. An Obsidian callout has no special meaning to Python-Markdown at all: it renders as an ordinary blockquote, and the same `[!note]-` marker text leaks into it.
- **Quartz** (remark/rehype) keeps raw HTML by default and renders `<details>` the same way, and, being a CommonMark-based pipeline, also parses the blank-line-separated Markdown inside it. An Obsidian callout again degrades to a plain blockquote with the marker text showing, because Quartz's default pipeline does not special-case Obsidian's callout syntax.

`<details>` is the one form that is genuinely collapsible on two of the four renderers (GitHub, Obsidian) and, on the other two, degrades to a plain but clean, fully visible block with no leaked marker syntax. An Obsidian callout is collapsible on exactly one renderer and leaks its own marker text as visible noise on the other three. That asymmetry, read off the renderers themselves rather than assumed, is why `<details>` is the convention here.

Open by default (`<details open>`), not collapsed, because F17's acceptance is that a first-time PM can understand a section without switching to source mode; a block that is visible but still requires a click before showing anything would fail that on the first pass. The summary text is the fixed word "Guidance" on every block, so it is one predictable string to look for, to keep, or to delete.

**Producing the clean artifact.** The template's own intro blockquote says to delete every `<details>...</details>` block before publishing a filled document; here is the mechanical way to do it, since "delete it by hand while filling in the document" is exactly the step this finding exists to make unnecessary to *remember*, even though it stays necessary to *do*. From the repository root:

```bash
python3 -c "
import re, sys
path = sys.argv[1]
text = open(path, encoding='utf-8').read()
clean = re.sub(r'\n?<details open>\n<summary>Guidance</summary>\n\n.*?\n\n</details>\n?',
               '', text, flags=re.S)
open(path, 'w', encoding='utf-8').write(clean)
" products/my-product/definition/prd.md
```

This is the same shape of operation the old convention needed for HTML comments; only the pattern changed. It is intentionally a command a PM runs once on their own filled copy, not a tool this repository ships and maintains, because the templates under active guidance-migration change what the pattern has to match, and a copy of it living in one place, this file, is easier to keep current than a copy living in a maintained tool and a second copy living in this documentation.

**What this covers, and what it does not.** Only templates/definition/prd.md has migrated. Every other template in the tree still teaches through HTML comments, hidden in every renderer above exactly as F17 describes; migrating the rest is deferred to a follow-up and tracked, not silently dropped: `python3 tools/template_rubric.py` reports `hidden_guidance_share`, the fraction of a template's words that still sit inside a comment, for every template, alongside its existing flagship score, so the remaining migration has a number attached rather than a memory. A template scoring well on the flagship rubric can still hide all of its guidance; the two questions are independent on purpose, so a migration in one does not quietly move the other.

## What to avoid

- **Absolute links**: they break when the repository is cloned, forked, or rendered offline.
- **Raw HTML other than the guidance the templates already use**, either the `<!-- comment -->` form most templates still carry or the `<details>` form templates/definition/prd.md migrated to (see above): some renderers strip other raw HTML for security, so prefer standard Markdown for everything else.
- **Renaming files without updating links**: [../lint.py](../lint.py) will catch these, but only after the change is made.
- **Committing generated site output into this repository**: build artifacts belong in a separate deployment branch or repository.

## Recommended setup

Use **Obsidian** to read and work locally. It respects the file structure, renders Mermaid, and surfaces frontmatter as properties.

When you need to publish, build with **MkDocs Material** for a traditional documentation site, or **Quartz** for a graph-heavy knowledge base that matches the Obsidian experience.
