# Rendering this repository

Every file in Product Manager OS is plain Markdown. Layer files (templates, frameworks, knowledge, skills, agents, and os) carry a YAML frontmatter block with `layer`, `stage`, `gate`, `feeds`, `method` and `aliases`; SKILL.md files carry `name` and `description`, with those keys in a SKILL.graph.yml beside them. Links are relative Markdown links, checked by [../lint.py](../lint.py). The stage hub notes in os/maps/ (and docs/ARCHITECTURE.md, templates/architecture/system-design.md) also carry wikilinks, which lint.py checks against paths and aliases. Several files contain Mermaid code blocks, for example [templates/architecture/sequence-diagram.md](../templates/architecture/sequence-diagram.md) and [GRAPH.md](GRAPH.md). Mermaid blocks in templates render; the generated whole-tree graph in GRAPH.md is above Mermaid's default size limit and shows a size-exceeded notice on GitHub and in Obsidian, so read its tables instead.

This guide covers four ways to render the tree as a website or knowledge base.

## GitHub

Nothing to install. GitHub renders Markdown natively. Relative links work between files in the same repository. Mermaid diagrams render in file views and pull requests. YAML frontmatter appears as a small table at the top of a file. Clicking a link from one Markdown file to another stays inside GitHub's renderer. GitHub shows wikilinks as plain text; use the Markdown links beside them.

## Obsidian

1. Clone the repository, then open the repository folder as a vault in Obsidian.
2. Open **Settings**, then **Files and links**.
3. Turn the **Use Wikilinks** option off so new links stay as relative Markdown links ([../lint.py](../lint.py) checks relative links).
4. Set **New link format** to **Relative path to file**, so a link Obsidian inserts is the same relative path lint.py and GitHub resolve.
5. Frontmatter appears as properties at the top of the note (or in the Properties view pane).
6. The graph view draws the Markdown links and wikilinks in note bodies. The `feeds` and `method` keys are plain paths, shown as text properties, not as edges; the rendering of those declarations is [GRAPH.md](GRAPH.md), generated by tools/graph.py. The `aliases` key is honoured, so [[Design Review Skill]]-style links resolve through it.

## MkDocs with Material

MkDocs refuses a `docs_dir` that contains `mkdocs.yml`, and pointing it at the whole repository would publish every Python and JSON file as a static asset, so keep a small site project whose build step copies the Markdown (and the non-Markdown files those pages link, such as LICENSE and lint.py) into its `docs` folder; put `site_dir` outside that folder. MkDocs needs a wikilink plugin (for example mkdocs-roamlinks-plugin) or the hub notes' wikilinks stay text.

Minimal `mkdocs.yml`:

```yaml
site_name: Product Manager OS
theme:
  name: material
markdown_extensions:
  - pymdownx.superfences:
      custom_fences:
        - name: mermaid
          class: mermaid
          format: !!python/name:pymdownx.superfences.fence_code_format
```

Install and build commands:

```bash
pip install mkdocs-material
mkdocs serve   # preview locally
mkdocs build   # generate site/ output
```

## Quartz

Point Quartz's content folder at a copy of the repository's Markdown, then build and serve it. Quartz keeps backlinks and a graph view, converting relative links to site paths automatically. The graph view uses the same link structure that Obsidian builds. Deploy the generated site to any static host.

Commands:

```bash
npx quartz create   # choose an existing folder
npx quartz build --serve
```

Set `markdownLinkResolution` to `"relative"` in `quartz.config.ts`.

## What to avoid

- **Absolute links**: they break when the repository is cloned, forked, or rendered offline.
- **Raw HTML other than the guidance comments the templates already use, which every renderer here hides**: some renderers strip it for security, so prefer standard Markdown.
- **Renaming files without updating links**: [../lint.py](../lint.py) will catch these, but only after the change is made.
- **Committing generated site output into this repository**: build artifacts belong in a separate deployment branch or repository.

## Recommended setup

Use **Obsidian** to read and work locally. It respects the file structure, renders Mermaid, and surfaces frontmatter as properties.

When you need to publish, build with **MkDocs Material** for a traditional documentation site, or **Quartz** for a graph-heavy knowledge base that matches the Obsidian experience.
