## Rules for every design file

- **The journey wins.** Where this sheet and [sahulat-journey.md](sahulat-journey.md) could be read two ways, the journey's reading holds. No design file moves a journey date, owner, outcome, score or gate attempt, and no N row is restated here with a different value.
- **Two sources of numbers, nothing else.** A design file cites journey rows by their own ids (N66, AC-8, T4) and this sheet's rows by SD id. Firmness uses the journey's words: measured, estimate, target, assumption, quoted or decided.
- **The prefix is SD.** SD is unused anywhere in the journey, its fourteen artifacts, the coverage sheet or any example. The identifiers below are checked against the journey's identifier table, the coverage sheet's identifier tables and every example that already exists before they are claimed.
- **No gate outcome.** No design example asserts a pass-2 gate outcome the journey has not recorded: Gate 1 of the second pass is not scheduled, exactly as the coverage sheet leaves it, and a design example treats that the same way.

## Reconciliation notes

These are the places where a careless design example would contradict the journey or the coverage sheet, with the reading every design file in this set follows.

1. **What pass 2 keeps from pass 1.** The journey says the next pass "discards Kamran and the pay-from-balance signal while keeping bill lookup, the USSD state machine and the BillBridge integration." Design examples read "the USSD state machine" as ADR-2's two-phase state machine with its idempotency key, and carry forward AC-7 and AC-8's dropped-session behaviour (a session that drops after the debit, and one that drops before it) as the screens' unhappy paths, unchanged by D8. The N66 session ceiling, 180 seconds on Falak Telecom's gateway, is the same hard limit pass 1 designed against; no design example gives pass 2 a longer session.
2. **What pass 2 discards.** Kamran (P3, the ASSUMPTION persona) and M2 (the balance-held-48-hours hypothesis) are gone. No design example screens, string table or state diagram below is drawn for a customer holding a balance to pay from; every screen is drawn for the agent-initiated, cash-in-hand flow the coverage sheet's service blueprint and design sprint describe.
3. **No pass-2 gate outcome exists.** The coverage sheet is explicit that Gate 1 of the second pass is not scheduled and leaves the question open with Hira Baig. Design examples built against this sheet state what a screen or string does, never that a gate has accepted it. Where a design example needs a review checkpoint, it names the design sprint's decision D9 (2026-09-18, agent-initiated and customer-confirmed into the customer's own wallet) or the sprint questions SQ1 and SQ2, never a gate.
4. **Wording quoted, not re-derived.** AC-2 (unknown reference), AC-12 (reminder SMS and opt-out) and AC-13 (tier limit refused with the limit named) are quoted exactly as [sahulat-acceptance-criteria.md](sahulat-acceptance-criteria.md) and the journey's N56 give them; a design file that needs a string for one of these states shows the acceptance criterion's own wording rather than writing a new sentence for it. N56's thresholds (lookup at 8 seconds p95, SMS confirmation within 60 seconds, a dropped-session status SMS within 2 minutes, the 24-hour "already paid" window, support lookup within 5 seconds, a failed-posting reversal within 24 hours, cash-in credit spendable within 30 seconds) are copied unchanged into any design file that tests against a timing budget; none of the seven is loosened.
5. **Agent-keyed, not customer-keyed.** The coverage sheet's service blueprint and E6 ("she gave me her PIN so I could do the bill") describe the agent keying the payment on his own handset or the customer's phone today. Design examples for pass 2 draw both paths as AS-3 (customers confirming on their own phone without handing over the PIN) is still marked "test", not "true": a screen set may design for no-PIN-shared confirmation, but no design example states that it already works in the field.
6. **The agent-handset app carries Urdu, on the confirmation screen, in this pass.** SD10 and SD11 record a device test, 2026-09-19, of Urdu Nasta'liq glyphs and line height on the agent-app confirmation screen: this is not a hypothetical for a later pass, it is this sheet's own dated fact. Any design example that scopes the agent app is read against that fact: the app is not English-only in pass 2. Where a string on that screen has no Urdu text yet, the design example marks the row Open (translation pending) rather than stating Urdu is out of scope.
