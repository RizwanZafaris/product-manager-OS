## 1. Endpoints

| Operation | Method and path (or event name) | Purpose | Idempotent? How? | Auth scope required |
|---|---|---|---|---|
| Create authorisation | `POST /v1/authorisations` | Authorise a card payment through Kestrel hosted fields for web and app, or through the Kestrel terminal SDK for the kiosk PIN pad, and invoke step-up per BR-005 (HARBOURGATE-S1, S2, S10; AC-11) | Yes: `Idempotency-Key` header, required, 24 h dedupe window (N61) | `payments:authorise` |
| Get authorisation | `GET /v1/authorisations/{id}` | Read the current status, provider, reason class and trace id for an authorisation (HARBOURGATE-S3) | N/A, read-only | `payments:read` |
| Capture authorisation | `POST /v1/authorisations/{id}/capture` | Capture at dispatch, never at authorisation time, per BR-006 (HARBOURGATE-S11; AC-12) | Yes: a repeat call for the same authorisation id returns the existing captured state rather than capturing twice | `payments:capture` |
| Void authorisation | `POST /v1/authorisations/{id}/void` | Void an authorisation with no dispatch inside 24 h, per BR-006 (HARBOURGATE-S11; AC-12) | Yes: a repeat call on an already-voided authorisation returns the existing state | `payments:void` |
| Create refund | `POST /v1/refunds` | Refund routed to the provider that authorised the order, through Kestrel directly or through Quay's legacy adapter until 2026-11-15 (BR-002, N50), per BR-002 (HARBOURGATE-S5; AC-7) | Yes: `Idempotency-Key` header, required, 24 h dedupe window (N61) | `refunds:write` |
| Status event | `payment.status_changed` (event) | Notify a subscriber that an authorisation, capture, void or refund changed state; feeds the order service and the decline event stream | At-least-once delivery; every event carries an event id and the consumer dedupes on it | `payments:read` (subscription) |

Web checkout and the app call Create authorisation and Get authorisation directly, with a `payments:authorise` session-scoped token that cannot call Capture or Void. The kiosk completes the card-present step in the Kestrel terminal SDK (DEP-1, I-3), Kestrel's own certified integration rather than the retired contractor's code (I-7), then calls Create authorisation itself with the `terminal_transaction_reference` the SDK returns. Capture and Void are never called by a checkout client: capture is called by the order service on dispatch, scoped `payments:capture`, and void by the Quay core service on the 24 h timer, scoped `payments:void` (system design component table; not the reconciliation service, which only matches settlement files against the ledger), both per BR-006. A call to Capture or Void carrying `payments:authorise` instead of the matching scope is rejected (403, see section 4). Refund is called by the order service and by finance operations tooling, never by a checkout client, so a customer-driven retry cannot itself trigger a refund.

Quay's own worst case before it resolves a kiosk authorisation, its 8 s call plus a 2 s wait plus a further 8 s if the retry itself needs the full timeout (target, N61), is longer than the kiosk's own 10 s BR-004 fallback, so a kiosk can show "pay at the till" before Quay's attempt has finished. What happens to an authorisation that then lands after the kiosk has already sent the customer to the till, where it would otherwise sit until BR-006's 24 h void while the customer also pays a second time, is not resolved on the data sheet. Interim rule until this is set: BR-006's void-on-no-dispatch-within-24-h behaviour is the only backstop that exists today, so a late authorisation lands and sits authorised, not captured, until that 24 h window closes; it is not voided immediately and the till is not notified, so the double-payment window this paragraph describes is not closed by BR-006 alone. [OPEN: owner Bea Lindqvist, before the 2026-11-13 peak change freeze (N64), since kiosk traffic has been live on every shop since 2026-08-17 (Tidewater cohort 3, N71) and this exposure is live in production today; tracked as R15 in the risk register.]

## 2. Schemas

Full shapes live in the spec file above; a reviewer needs these fields.

**`POST /v1/authorisations`**
Request: `order_id` (string, required; Quay looks up the order total itself, see below), `currency` (string, required, ISO 4217), `payment_method` (for web and app: hosted-fields session token, string, required; for kiosk: `terminal_transaction_reference`, string, required, returned by the Kestrel terminal SDK after the PIN pad completes, not a hosted-fields token), `capture_mode` (enum `manual`, fixed by BR-006). `amount_minor` and `customer_present` are not caller-supplied: Quay reads `amount_minor` from `order_id`'s own total (any caller-sent amount is ignored) and derives `customer_present` from the credential type, `true` for a kiosk terminal transaction reference (card present at the PIN pad) and `false` for a web or app session token, so a browser cannot claim card-present treatment and skip the BR-005 step-up.
Response: `id` (string, UUID), `status` (enum `authorised`, `requires_action`, `declined`), `provider` (enum `kestrel`, `marlowe`, `tidewater`; `kestrel` for every cohort ADR-0003 has shifted to Kestrel directly, and for every new authorisation once a given legacy provider's own last cohort has run, Marlowe's 2026-07-20 and Tidewater's 2026-08-17 (N71); `marlowe` or `tidewater` for an order still on that provider's cohort mid-drain before its cutover date, and permanently thereafter on this same response shape for Get authorisation and on Create refund's response, for any order that provider actually authorised, since the enum records history and is never retired), `reason_class` (string enum, present when `status=declined`: at minimum `card_declined`; `provider_unavailable` is not a decline and never appears here, since it is Kestrel or a legacy provider being unreachable, not the card being refused, see the 503 row in section 4), `action` (present when `status=requires_action`: `{challenge_url: string}`), `trace_id` (string).

**`POST /v1/authorisations/{id}/capture`**
Request: no body beyond the path id.
Response: `id`, `status` (enum `captured`, unchanged if already captured), `captured_amount_minor` (integer), `trace_id`.

**`POST /v1/authorisations/{id}/void`**
Request: no body beyond the path id.
Response: `id`, `status` (enum `voided`, unchanged if already voided), `trace_id`.

**`GET /v1/authorisations/{id}`**
Response: same shape as the Create authorisation response above, reflecting current state.

**`POST /v1/refunds`**
Request: `authorisation_id` (string, required), `amount_minor` (integer, required, > 0, <= captured amount minus amount already refunded on this authorisation, so repeated partial refunds cannot together exceed the capture), `reason` (enum `duplicate`, `customer_request`, `fraud`, required).
Response: `id`, `status` (enum `pending`, `succeeded`, `failed`), `provider` (enum `kestrel`, `marlowe`, `tidewater`; the authorising provider), `trace_id`.

**`payment.status_changed`**
Body: `event_id`, `authorisation_id`, `order_id`, `provider` (enum as above), `status` (enum: the union of the authorisation, capture, void and refund status enums above), `reason_class` (string, nullable), `trace_id`, `occurred_at` (string, ISO 8601 timestamp).

## 3. Authentication and authorization

- Mechanism: `OAuth 2.0 client credentials` for service consumers, order service and finance operations tooling, the same mechanism Quay itself presents to Kestrel on I-1. Web checkout and the app receive a short-lived session-scoped token issued by Quay when a checkout session opens, so no static client secret is held in a browser or the app binary. The kiosk authenticates with a device-bound API key, one per kiosk (N2, 61 kiosks, one per shop), provisioned by store operations during the DEP-5 firmware rollout rather than issued alongside the Kestrel terminal SDK certification itself (DEP-1 delivered 2026-07-09 covers the SDK; DEP-5, delivered 2026-07-30, is the per-shop rollout that provisions the key on each device).
- Token or key lifetime and rotation: session-scoped web and app tokens expire when the checkout session ends. Service credentials and kiosk device keys rotate on personnel change or suspected compromise; owner Bea Lindqvist. Because Quay sits inside PCI DSS assessment scope (N55), requirement 8.6.3 also applies: application and system account credentials must be rotated at a periodic interval set by a targeted risk analysis, not only on an event. [OPEN: the periodic interval itself is not on the data sheet; owner Hamid Qureshi, to run the targeted risk analysis and set it before the DEP-7 booking is committed (2026-11-20), for the post-sunset reassessment needed by the 2026-12-15 sunset.]
- Authorization model: `payments:authorise` may call Create authorisation and Get authorisation from web, app and kiosk clients. `payments:capture` is scoped to the order service only; `payments:void` is scoped to the Quay core service only (the void timer owner per the system design component table, not the reconciliation service). Neither is ever issued to a checkout client. `refunds:write` is scoped to the order service and finance operations tooling only. `payments:read` covers the status event subscription. A call carrying the wrong scope for the operation it targets receives 403 (section 4).

## 4. Errors

| Condition | Status or code | Error body shape | Consumer's correct reaction | Retryable? |
|---|---|---|---|---|
| Card declined by Kestrel, or Marlowe/Tidewater while their cohort is still mid-drain | 402 Payment Required | `{code: "card_declined", reason_class, trace_id}` | Show the decline with its reason class; offer exactly one retry with a different payment method, per BR-001, HARBOURGATE-S3 and AC-5 | No, never on the same card |
| Kestrel unreachable, or times out after Quay's own 8 s call and one retry after a 2 s wait on a network error (target, N61) | 503 Service Unavailable | `{code: "provider_unavailable", trace_id}` | The outcome at Kestrel is unknown, not "nothing was authorised". This is not a card decline, so BR-001's one-retry-on-a-different-method rule does not apply: checkout shows "card payments are temporarily unavailable, try again shortly", the same as I-1's stated failure behaviour, not a decline screen. Retry the same order with the identical `Idempotency-Key`; Quay forwards that key to Kestrel, so Kestrel returns the original result instead of authorising the card a second time (N61). A `provider_unavailable` outcome is not stored as the key's final response, so a same-key retry re-sends to Kestrel carrying the forwarded key, and Kestrel's dedupe returns the original result if the first attempt did land | Yes, with the identical `Idempotency-Key` |
| `Idempotency-Key` reused with a different request body | 409 Conflict | `{code: "idempotency_conflict", original_authorisation_id, trace_id}` | Do not resend with the same key. Call `GET /v1/authorisations/{original_authorisation_id}` using the id returned in this body to see the original outcome, rather than guessing | No |
| `Idempotency-Key` reused with the same body while the original request is still processing | 409 Conflict | `{code: "idempotency_in_flight", trace_id}` | Do not resend. Wait briefly, then poll `GET /v1/authorisations/{id}` once the id is known, or wait for `payment.status_changed` if subscribed | No, poll instead |
| `Idempotency-Key` header missing on Create authorisation or Create refund | 400 Bad Request | `{code: "missing_idempotency_key", trace_id}` | Add the header and resend as a new request; this was never accepted, so nothing to deduplicate against | No, until the header is added |
| Request fails schema validation (missing or malformed required field) | 400 Bad Request | `{code: "invalid_request", field, trace_id}` | Fix the named field; do not resend unchanged | No |
| Credential's scope does not cover the operation called (e.g. `payments:authorise` calling Capture) | 403 Forbidden | `{code: "insufficient_scope", trace_id}` | Call with the credential scoped for this operation, per section 3; resending with the same credential repeats the error | No |
| Unknown authorisation id | 404 Not Found | `{code: "authorisation_not_found", trace_id}` | Verify the id; do not resend the same id expecting a different result | No |
| Capture or Void called on an authorisation BR-006 already voided (the dispatch-at-hour-25 race) | 409 Conflict | `{code: "authorisation_voided", trace_id}` | The payment must be re-authorised; never retry the original capture | No |
| Void called on an authorisation already captured | 409 Conflict | `{code: "authorisation_captured", trace_id}` | No action from this call; if the capture itself needs reversing, use Create refund instead | No |
| Refund called on an authorisation not yet captured | 422 Unprocessable Content | `{code: "authorisation_not_captured", trace_id}` | Wait until capture completes (BR-006), then retry the refund | Yes, after capture completes |
| Refund requested against an order a legacy provider (Marlowe or Tidewater) authorised, up to and including 2026-11-15 (BR-002, N50) | 201 Created, `status=pending` | `{id, status: "pending", provider: "marlowe"` or `"tidewater", trace_id}` | Not an error while BR-002 is active: Quay routes the refund through the legacy adapter to the authorising provider. (Rehearsal 2, N38, found this path returning 422 in error; that defect was fixed before rehearsal 3 and is not the contract.) | N/A |
| Refund requested against a legacy-authorised order from 2026-11-16, after the legacy refund window closes (N50) | 422 Unprocessable Content | `{code: "legacy_refund_window_closed", trace_id}` | Not this API's job: hand off to finance operations, who refund through the provider portal within 5 working days, per BR-009. After the provider portal wind-down access ends (2027-06-15, N52), even that manual path is gone; that edge is [OPEN: owner Anneliese Vogt] and is not expected to arise, since returns windows on legacy-authorised orders (90 days, N50) close before portal access ends on 2027-06-15 (N52) | No |
| Step-up required before an authorisation can proceed | 200 OK, `status=requires_action` | `{status: "requires_action", action: {challenge_url}}` | Not an error. Redirect the customer to the challenge, then poll `GET /v1/authorisations/{id}` for the outcome (server-side subscribers to `payment.status_changed` may use the event instead; web and app checkout clients are not subscribers), per BR-005, HARBOURGATE-S10, AC-11 and the £250 / fraud-flag threshold in N57 | N/A |
| Refund amount exceeds the captured amount minus what has already been refunded on this authorisation | 422 Unprocessable Content | `{code: "amount_exceeds_refundable_balance", trace_id}` | Do not retry; surface to the caller | No |
| Rate limit exceeded | 429 Too Many Requests | `{code: "rate_limited"}`, `Retry-After` header | Wait until the `Retry-After` value has passed (it may be a number of seconds or an HTTP-date), then retry | Yes, after `Retry-After` |
| Unauthenticated or expired credential | 401 Unauthorized | `{code: "unauthenticated"}` | Refresh the credential once, then retry | Yes, after refreshing |
| Unexpected failure inside Quay | 500 Internal Server Error | `{code: "internal_error", trace_id}` | Retry once with backoff; if it persists, escalate with the trace id rather than looping | Yes, once |

The 402 (Kestrel decline), 503 (provider unavailable) and 409 rows are the distinction the checkout clients must honour, and the one the cascade rule got wrong: the first means the issuer, or Kestrel's risk rules, declined this card, and this API will not resubmit it; the second means Kestrel itself, not the card, is the problem, the outcome is genuinely unknown rather than known-safe, and the safe response is the identical-key retry, not a decline and not a fresh authorisation attempt; 409 means the client itself is confused about what it already sent, and guessing again only compounds that. This contract deliberately follows the template's own worked example on 409 versus 422 rather than the IETF "Idempotency-Key HTTP Header Field" draft's recommendation to split a payload mismatch into 422 and reserve 409 for an in-flight retry; the row above for a same-key, same-body retry while the original is still processing keeps that in-flight case distinct without adopting the draft's status-code split.

## 5. Limits and versioning

- Rate limit: two limits, not one, and they must be read separately. (a) Quay's own inbound limit on its API consumers (web, app, the 61 kiosk device keys, the order service and finance tooling: five consumer classes; the reconciliation service holds no scope under section 3 and calls no operation in section 1, so it is not a consumer of this limit): 50 req/s total across all of them combined, not per consumer, [OPEN: per-consumer shares that sum to no more than 50 req/s are not sized on the data sheet; owner Bea Lindqvist]. (b) Quay's own outbound calls to Kestrel: also capped at 50 req/s total (N61), which is Kestrel's per-account ceiling on the Harbourgate MSA (N24, measured), not a figure Quay chose. Both sit below the payment table's write path, which breaks at 80 req/s (N24), so 50 req/s leaves headroom on either leg rather than sitting at the edge. Behavior at the limit, either leg: 429 with `Retry-After` (N61).
- Payload size limit: not sized in the data sheet. [OPEN: a defensive body-size ceiling, owner Bea Lindqvist, to be set before the 2026-11-13 peak change freeze (N64); no successor to the 2026-06-05 load test (N23, N24) is recorded on the data sheet, so this needs a fresh load test rather than assuming one exists.]
- Versioning scheme: URL version (`/v1/`), additive-only within a version; a breaking change ships as `/v2/` rather than changing `/v1/` under a consumer's feet.
- Breaking change policy: advance notice to every consumer named in section 1, posted in the payments channel, before any breaking change ships. [OPEN: the notice period itself is not on the data sheet under any row; until Bea Lindqvist sets one, plan against 90 days as the floor, the same minimum Harbourgate's own contracts require of Marlowe and Tidewater (N51), borrowed rather than invented.] No breaking change and no non-rollback change ships during the peak change freeze, 2026-11-13 to 2026-12-04 (N64).
- Deprecation contract: an old version stays callable for 90 days after its replacement ships, announced with a removal date, never withdrawn silently. Ninety days is not a number this contract invented for itself: it is the same minimum notice Harbourgate's own contracts require of Marlowe and Tidewater (N51), applied here to Quay's own consumers rather than to an external counterparty.
