# Content and Microcopy Audit: Sahulat second-pass USSD menu and SMS strings

Fills [frameworks/design/content-microcopy-audit.md](../frameworks/design/content-microcopy-audit.md). Everything here is invented: Sahulat is a fictional mobile-money wallet in Pakistan run by a fictional licensed electronic-money institution, the people, agents, customers, billers and telco are fiction, and every number and string is ILLUSTRATIVE, chosen to show the audit mechanics and the channel arithmetic on a two-script product and not to describe any real wallet, gateway or regulator. See the [examples index](README.md).

**Owner:** Hira Baig, Product Manager, the only PM in the company · **Date:** 2026-09-26 · **Audit run:** 2026-09-24 to 2026-09-26 · **Scope:** second-pass USSD menu pages and SMS strings, English source and Urdu translation, against the [Sahulat UX writing guide](sahulat-ux-writing-guide.md) · **Anchor:** [sahulat-journey.md](sahulat-journey.md)

## What it is for

Pass 2 rewrote every USSD and SMS string to name the agent's role and the customer's confirmation, and the Urdu translation of two of them arrived from the vendor mid-pass. This audit walks all twelve strings, in every state the pass-2 screens can be in, against the nine rules below: does the string say what happened, does it say how to fix it, does it avoid a banned word, does it avoid blaming the reader, is the confirmation step on the actual irreversible action rather than a reversible one it is habituating past, does the term match the glossary, does the string fit the channel's character budget in its encoding, does the translation have room to grow inside that budget, and is every date, amount, and number drawn from the reader's locale rather than hard coded. It closes the same DESIGN-stage gap the blank names: a screen reviewed for layout and never for what it actually tells the agent standing over the customer or the customer reading a debit confirmation on a feature phone.

## Run it when

This audit runs before Gate 3 of pass 2, on every screen and flow in the pass-2 release that carries new or changed user-facing text. It covers the second-pass USSD menu pages (the agent-initiated, customer-confirmed flow) and the SMS strings that accompany them. The strings were rewritten after D8 (2026-08-28) and D9 (2026-09-18) to name the agent's role and the customer's confirmation, and the Urdu translations for the confirmation SMS (S05) and the payment-declined SMS (S09) arrived from the localisation vendor on 2026-09-22, triggering the second pass of this audit on those two strings specifically.

## Inputs you need first

- The product's design brief, in particular section 6, Deliverables: the screens, flows, and fidelity levels this audit inventories against. For pass 2, the surfaces are the USSD menu pages (pages 1 through 4 of the agent-initiated flow) and the SMS confirmation and error strings. The USSD gateway is Falak Telecom's, subject to a vendor-enforced page limit narrower than the 3GPP maximum (see the channel arithmetic in step 2).
- The product's writing guide, [sahulat-ux-writing-guide.md](sahulat-ux-writing-guide.md), for its glossary of approved terms and its own banned word list, layered on top of the house list below.
- The channel plan for each string: in-app screen, push notification, email, SMS, or USSD, because the channel sets the character limit and the encoding. In pass 2, the customer receives SMS only on Falak Telecom's network (no push on feature phones; email is not a channel for this cohort). The agent receives an in-app notification on the agent handset (Android, GSM-7 capable).
- The confirmation inventory from the design brief or the ADRs: which actions the product already treats as serious or irreversible. In pass 2, the only irreversible action in scope is the debit from the customer's wallet after confirmation, which ADR-2 makes a two-phase state machine with an idempotency key. Every other step is reversible within the session (the agent can back out before sending the confirm prompt; the customer can decline the confirm prompt).

### 2. Per string, run the rule check

For every row from step 1, answer each rule yes or no. A string that cannot honestly be marked yes is a fail on that rule, whatever the deadline says.

| Rule | What it checks | Pass means |
|---|---|---|
| States what happened | The string names the event, not a code or a generic label | "Payment stopped because the biller did not accept", not "Error: payment failed" |
| States how to fix | The string tells the reader the next action | "Visit an agent or bank to put money in, then ask your agent again" |
| No banned word | The string avoids the list below | Neither the house list nor the product's own list is present |
| No blame | The string does not accuse the reader of an error they did not knowingly make | No "you forgot", no implied fault for a system failure |
| Confirmation gated correctly | A confirmation step appears only for a serious or irreversible action, and the reversible ones offer undo instead | See the confirmation rule below |
| Terminology matches the glossary | The term used matches the product's writing guide glossary, not a synonym | "Agent", never "assistant" for the same role |
| Fits the channel limit | The string fits inside the character budget computed for its channel and encoding | See the channel arithmetic below |
| Expansion headroom | The layout or channel budget leaves the stated headroom percentage for translation growth | See the headroom convention below |
| Locale formatting via CLDR | Dates, numbers, and currency are formatted from the reader's locale data, never hard coded to one locale | A date renders as the reader's locale expects, not as the source locale wrote it |

**No banned word, the house list.** Adapted under the Open Government Licence v3.0 from the GOV.UK Design System's error message guidance (evidence class: platform convention). Do not use:

- technical jargon such as "form post error", "unspecified error", or an internal error code shown as-is
- "forbidden", "illegal", "you forgot", or "prohibited"
- "please", because it implies the action is optional
- "sorry", because it does not help the reader fix the problem
- "valid" or "invalid", because they add nothing to the message
- humorous or informal language such as "oops"

Layer the product's own banned word list from [sahulat-ux-writing-guide.md](sahulat-ux-writing-guide.md) on top of this one; the two lists are checked together as a single yes or no per string. Jakob Nielsen, "Error Message Guidelines" (Nielsen Norman Group, 2001; evidence class: practitioner heuristic), recommends a positive, specific, non-blaming tone as what makes an error message actually get read and acted on.

**Confirmation gated correctly.** Per Jakob Nielsen, "Confirmation Dialogs Can Prevent User Errors (If Not Overused)" (Nielsen Norman Group, 2018; evidence class: practitioner heuristic), a confirmation step earns its place only when the consequence is serious or hard to reverse; on routine or frequent actions it becomes a habitual click-through and stops preventing anything. Mark this rule pass when a confirmation appears on an action the design brief or an ADR has named serious or irreversible, and mark it pass when a reversible action skips confirmation in favor of an undo affordance instead. Mark it fail in both directions: a missing confirmation on an irreversible action, and a confirmation dialog defending a reversible one.

**Channel arithmetic, character limit.** Compute the limit per script and encoding, never assume the Latin-script limit applies everywhere:

- GSM-7 encoding (Latin scripts the standard covers): 160 characters in a single SMS, 153 characters per segment once the message is split across segments (the segment headers cost 7 characters each).
- UCS-2 encoding (scripts GSM-7 does not cover, including Urdu and Arabic): 70 characters in a single SMS, 67 characters per segment.
- USSD: at most 182 characters per page in GSM-7 (standard-derived, 3GPP TS 23.038 and TS 23.090: 182 GSM-7 characters packed into a 160-octet payload), roughly 80 characters in UCS-2; gateways often enforce less, commonly 160, so confirm the actual figure with the gateway contract rather than assuming the standard's maximum (evidence class: vendor claim, confirm per integration).

For this audit, the Falak Telecom USSD gateway contract specifies a maximum of 160 GSM-7 characters per menu page (N66 names the session ceiling, not the per-page limit; the gateway specification for per-page length is a separate line in the contract). The audit uses 160 as the USSD page budget for English (GSM-7). For SMS, the Falak Telecom contract specifies PKR 1.2 per message (N40) and a 160-character GSM-7 single-segment budget; no multi-segment SMS is sent in the flow (the product sends one message per event, so a multi-segment send is a fail on this rule).

**Expansion headroom convention.** Reserve headroom against the source-language character count before the layout or the channel budget is locked: a stated convention is 30 percent for most Western European target languages (evidence class: practitioner heuristic; confirm per target language, because some target languages contract rather than expand). For Urdu (UCS-2), the convention does not directly apply (the 30 percent expansion figure is calibrated against GSM-7 Latin expansion, not against the encoding-switch cost from a 160-character GSM-7 source to a 70-character UCS-2 target). The headroom check for Urdu is therefore: does the source string, when translated, fit the 70-character UCS-2 single-segment budget for SMS? Mark the rule fail when the layout has no room to grow, whatever the source-language string currently measures.

**Locale formatting via CLDR.** Dates, numbers, currency, and list separators are drawn from Unicode CLDR locale data for the reader's locale rather than hard coded to the string's source locale (evidence class: standard). A date field that always renders day-month-year is a fail on this rule for any reader whose locale expects month-day-year, even if the string itself passes every other rule. For Sahulat pass 2, the relevant locale is `ur-PK` for Urdu customers and `en-PK` for English. The `{month}` and `{amount}` fields are formatted server-side from the customer's preferred locale setting at account opening; the audit checks that the format string, not the template text, is locale-aware.

**Confirmation note on S01.** Page 1 ("Reply 1 to pay or 2 to cancel") is the string most likely to become a habitual click-through, because the agent is standing over the customer and the customer reads it in the middle of a queue. ADR-2 places the irreversible gate at the debit (page 2 confirmation), not at page 1. Page 1 is the agent's introduction, not the customer's confirmation of an irreversible action. A confirmation dialog on a reversible step, and a confirmation that does not name the consequence, is the pattern Nielsen's 2018 article calls "a habitual click-through and stops preventing anything." The fix is not to delete page 1 (the flow needs the agent's introduction to name who is paying), but to strip it of confirmation language: it should state what is happening, not ask for a yes-or-no on a step that can still be backed out of.

**S05-U, the Urdu translation detail.** The vendor delivered S05-U on 2026-09-22. It runs to 74 UCS-2 characters. The Falak Telecom SMS gateway (N40's PKR 1.2 rate is per message) delivers a single message per segment, so a 74-character Urdu string is split to 2 segments, costing PKR 2.4 per delivery (2 x PKR 1.2). This is a cost failure, not only a content failure: at 31,200 bills (N42), the additional segment cost for S05-U alone is 31,200 x PKR 1.2 = PKR 37,440 a month on every delivery that carries this string. The fix is to cut the Urdu draft to 70 characters or fewer; the English source (78 characters, GSM-7) is already over the 70-character UCS-2 budget, so the Urdu draft cannot be a word-for-word expansion of the English source and must be rewritten to the 70-character UCS-2 budget. The headroom convention's 30 percent figure is calibrated against GSM-7-to-GSM-7 expansion in Western European scripts and does not transfer to the GSM-7-to-UCS-2 transition; the 74-over-70 arithmetic is the check, not the convention.

## Reading the result

The pass rates point at two rules, not scattered screens. "States how to fix" at 50 percent (6 of 12) is the screen-level problem: half the strings name the event and then stop, leaving the reader with no instruction on what to do next, which is exactly the pattern that produces E4's blind redial when the event is "payment stopped" and the instruction is absent. Read the fail list by rule before reading it by screen: S01, S02, S04, S06, S10 and S05-U all fail the same rule for the same underlying cause (the copy names the event and stops, or the vendor omitted the instruction), which is one rewrite pass over the event-plus-instruction pattern, not six separate reviews.

"Confirmation gated correctly" at 50 percent (1 of 2) is the more severe finding, because it is the rule the blank's reading section names as a Gate 3 blocker: a string that fails confirmation gating ships as either a destructive action with no warning or a message the reader never receives in full. S01 is the reversible-step confirmation, and the fix is a language strip, not a deletion (the flow needs the agent's introduction to name who is paying), so this is fixable in the rewrite pass. S03, the irreversible-debit confirmation, is correctly gated and passes.

The channel arithmetic (fits channel limit, expansion headroom) carries the cost exposure: S05-U's 74-over-70 UCS-2 characters is a delivered count and means 31,200 additional PKR 1.2 segment costs a month at current bill volume (N42); S07 and S08 carry the same encoding-boundary risk in their Urdu targets, and the S07 and S08 Urdu counts (74 and 72 characters) are estimates derived from the 1.2x expansion factor, not delivered drafts, so each must be re-counted when the vendor's text lands. Three strings' Urdu translations must be rewritten to the 70-character UCS-2 single-segment budget, or the flow must authorize a 2-segment SMS for those events with the cost line added to the rate plan. This is the localisation-and-RTL-checklist carry-forward row.

The locale formatting fail (S09's hard-coded phone number) is a one-line change to the string template and is not a content-design decision; it is a template plumbing change, owned by the content owner but verified by the localisation lead.

The two no-banned-word rules at 100 percent mean the writing guide is doing its job: the copy pass that touched the error and SMS states did not reintroduce "sorry", "please", "oops", or a raw error code. The pass rates are confirming on those rules, not catching. The 100 percent pass on "no blame" (the rule Nielsen's 2001 article argues is the one that makes an error message get read and acted on) is worth naming explicitly, because the pass-2 copy's job is to tell Shazia that the system failed, not that she failed, and it holds on every error string.

S07's glossary-layer "your" flag did not rise to the banned-word fail because the house list does not ban "your" and the glossary's balance-context note is a style guide, not a banned-word list; the pass stands, but the style note is logged for the glossary owner (Hira) to resolve: either the glossary bans "your" in a trust-account context, or the glossary note is removed so the style guide and the banned-word list stay one and the same.

## The trap

Auditing the English strings and shipping the translations unaudited. S05-U (the Urdu draft of the payment-success SMS) is this trap caught before it shipped rather than after: it passed the no-banned-word and no-blame rules because the vendor did not introduce a blame or jargon word, and it fails two rules the source-language audit would never have caught on its own. First, it omitted the "do not dial again" instruction (T4, E4, AC-7's reason for existing) that the English source carries and that the customer's redial-prevention depends on. Second, it runs to 74 UCS-2 characters against the 70-character single-segment budget, a cost failure at PKR 2.4 per delivery (2 x N40's PKR 1.2) on 31,200 deliveries a month (N42). The Urdu translations for S07 and S08 carry the same encoding-boundary risk: the S07 Urdu count of 74 characters and the S08 Urdu count of 72 characters are both estimates derived from the 1.2x expansion factor (neither draft has reached the vendor's delivery date), checked against the 70-character budget. Run step 2 again on every shipped translation, not only on the source-language draft; the Sahulat pass-2 audit runs step 2 on S05-U on the day the vendor delivered it, not at the end of the pass.
