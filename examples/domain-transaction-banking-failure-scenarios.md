## 1. Scenario table

Blast radius is written worst case first. Detection means how Westgate knows within minutes, without a client telling us: the transaction banking card's rule is that "customer report" is disqualified as a detection method here, because the client's payroll clock runs faster than a support ticket, so no row below uses it. Recovery names steps, an owner, and a time to recover.

| ID | Scenario | Blast radius | Detection | Recovery | Data loss risk |
|---|---|---|---|---|---|
| FS-4 | Bulk payroll file, 2,400 rows, partially rejects at the scheme gateway: 2,391 rows post, 9 fail validation | The 9 employees on the failed rows are not paid on cycle; the client's own portal shows a file-accepted notice that is only 99.6% true | Scheme-gateway rejection webhook parsed row by row, not file by file; a file-level accepted response alone hides this | Auto-flag the 9 rows to the client's maker within 5 minutes with the reject reason per row; owner: Nadia Okonkwo, Treasury Desk; manual re-submission before the scheme's next cut-off, same business day | None directly; rejected rows are never debited, but the client's own ERP may already record them as paid, a reconciliation break rather than a money-loss event |
| FS-5 | Payroll file arrives after the scheme's same-day cut-off: submitted 16:02, acceptance at 16:07, against a published cut-off of 16:00 | The whole file, all 2,400 rows of the day's run, slips to the next business day's value date; the client's payroll date, not the bank's, is missed | Westgate's own ingest timestamp versus the scheme's published cut-off, evaluated on every submission and alarmed at the moment of acceptance, before any client contact | Hold the file in the pre-cutoff queue, notify the maker with the actual value date at 16:07, offer same-business-day resubmission before the next window (17:30); owner: Marcus Hale, Payments Operations; under 30 minutes if the file is re-trimmed, next business day if not | None; the file is accepted and processed, it is the value date that moves |
| FS-6 | Duplicate submission of the same file ID: the client's ERP retries on an HTTP timeout, and the same file ID is sent twice | If both land at the scheme, the payroll pays twice for every row that clears, worst case 2,400 double payments; detection upstream in Westgate is the point, not the scheme's | Duplicate file-ID guard on ingest, raising a duplicate-submission alert against the original send record within 60 seconds; the scheme's own duplicate handling is treated as a backstop, not the control | Suppress the second file, return the original file status to the client's ERP via the payment status report, and log the duplicate attempt with both submission timestamps for the auditor export; owner: Marcus Hale, Payments Operations; under 15 minutes | None, because the second file never leaves Westgate; if the guard fails the loss is a real double debit and an ERP break on every cleared row |
| FS-7 | Host-to-host SFTP key expires for one corporate client's connection | Every file from that client is refused at the SFTP boundary for as long as the key is stale, worst case the whole 2,400-row weekly run and any same-day file behind it; the client sees a connection error, not a business one | Key-expiry monitor and failed-authentication alarm on the SFTP boundary, alerted 14 days, 7 days and 24 hours before expiry, with a live "connection refused" alert raised within 5 minutes of the first such attempt | Rotate the key with the client's IT contact from the pre-agreed escrow process, re-drive any file the client says it sent, and confirm with the maker; owner: Elena Marsh, Client Connectivity; 4 hours to a working connection, same business day for the backlog | Possible: files the client believes it sent are not on Westgate's side and were never recorded; the client's ERP may already mark those rows as sent, so the status report is what rebuilds the record |
| FS-8 | ISO 20022 schema rejection after the scheme's migration: a row that was valid under the old MT mapping is refused under the new ISO 20022 mapping | Rows whose payload maps to the new mandatory fields (structured creditor postal address among them) are rejected row by row; a client whose beneficiary master is entirely unstructured sees the full file reject; in the September run one client's 2,400-row file rejected 640 rows on missing structured address fields, and on a bad day the whole file is refused | Schema-validation reject codes surfaced row by row through the gateway webhook, alarm on any pty of reject code indicating a schema breach, and a daily reconciliation of accepted-versus-rejected counts against the submission, within 15 minutes of the gateway response | Map the reject reason codes to the client's beneficiary master fields, hand the client's maker the per-row reason and the field path, and gate the same map through Westgate's own pre-submission validator so the client catches the same fault before the next cut-off; owner: Priya Raghavan, with scheme liaison through Marcus Hale; same business day for a re-trimmed file | None for rejected rows; possible for the 1,760 accepted rows if the client's ERP is not reconciled to the status report, because it may hold them as fully sent |
| FS-9 | Bank-holiday calendar mismatch: Westgate's calendar and the scheme's differ, and a file queued for a value date the scheme treats as a holiday | The whole bulk run queues in a "processing" state with no value date, which the treasurer reads as "tested", and on the wrong day the file can be released with a one-day value shift; worst case is the client's payroll landing a day late for every employee on the run | Value-date validity check on every queued file against the scheme's published calendar, plus a daily cross-check of the two calendars alarmed on any date where they disagree by more than one business day before the affected value date | Recompute the next valid value date against the scheme's calendar, notify the maker with the corrected date and the reason, and re-release the file; owner: Marcus Hale, Payments Operations; under 1 hour once the calendar difference is identified | None; the file is queued, not lost, but every downstream payroll date the client set is now wrong and the status report is the correction |

The arithmetic behind the numbers above: 2,400 rows in the payroll file; 2,391 post + 9 fail = 2,400, so the file-accepted notice is true for 2,391 / 2,400 = 99.625%, shown as 99.6%. Step 2's schema example: 2,400 - 640 = 1,760 rows accepted, so the rejected share is 640 / 2,400 = 26.666...%, shown as 26.7%. The cut-off margin behind FS-5 is 16:02 - 16:00 = 2 minutes late, and the file acceptance 16:07 - 16:00 = 7 minutes past cut-off.

## 2. Monitoring gaps found while writing this

Every "we would not know" discovered above becomes a row here and a change request against the observability pattern, on the same principle the transaction banking card uses for reconciliation breaks: the number that matters has to be on the surface where the person who can act on it will see it.

| Gap | Fix | Owner | Date |
|---|---|---|---|
| Westgate can see that a client's file was rejected, but has no row-level alert if the client simply does not re-submit before the next cut-off | Add a "rejected and not resubmitted" alert at cut-off minus 30 minutes, on every file that carries a rejection in the current session | Elena Marsh, Client Connectivity | 2026-10-02 |
| Duplicate file-ID detection depends on the client reusing the same file ID; a client that resends under a new ID is invisible to it | Extend the guard to match a content hash of the previous 7 days of files from the same client, not only the file ID | Marcus Hale, Payments Operations | 2026-10-16 |
| The SFTP key-expiry monitor exists but no one owns the client-side escalation when the 14-day alert is ignored | Name an escalation owner per client in the connectivity register and make the 7-day alert page a person, not a queue | Elena Marsh, Client Connectivity | 2026-09-25 |
| Pre-submission validation does not yet reproduce the scheme's ISO 20022 mandatory-field rules, so a client learns about a schema fault only after submission | Extend the validator to the scheme's published rulebook fields, with structured creditor address and structured remittance information first | Priya Raghavan | 2026-11-06 |
| The two bank-holiday calendars are reconciled monthly by hand and the difference surfaces only if someone reads the comparison | Replace with a daily automated cross-check and alarm on any divergence greater than one business day ahead of the affected value date | Marcus Hale, Payments Operations | 2026-10-09 |
| The payment status report back to the client's ERP is not monitored for delivery success; a rejected-and-corrected file that the ERP never hears about leaves the client's system wrong in the quiet direction | Add delivery-confirmation tracking on every status report, with an alert if a report is unsent or unacknowledged for more than 24 hours | Priya Raghavan | 2026-10-30 |

## 3. Rehearsal

- Scenarios rehearsed (game day or tabletop), with dates: FS-4 partial batch failure, tabletop on 2026-07-14 with Nadia Okonkwo and Marcus Hale, before the scheme migration; FS-8 ISO 20022 schema rejection, tabletop on 2026-09-08 in the same week as the migration rehearsals that produced the two-session migration dual-run schedule; FS-5 cut-off miss and FS-6 duplicate submission, tabletop on 2026-09-09; FS-7 expired SFTP key, game day on 2026-09-10 against a staging connection, with a real client contact not in the room so the escalation path was exercised end to end; FS-9 bank-holiday calendar mismatch, scheduled for 2026-10-21 and not yet run.
- The scenario we most doubt our recovery steps for: FS-6, duplicate submission. The guard is a single ingest check against a file ID plus a content hash, and no rehearsal has yet tested a duplicate that arrives with a genuinely different hash and a genuinely identical set of rows, which is what a client's ERP retry could produce if it re-generates the file. Until that is rehearsed, FS-6's recovery time of under 15 minutes rests on a case we have not seen fail.
