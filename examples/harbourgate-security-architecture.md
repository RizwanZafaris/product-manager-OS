## 1. Trust boundaries

| # | Boundary | What crosses it | Trust change |
|---|---|---|---|
| 1 | Customer browser or app to Quay's checkout API | Order and customer identifiers; no card number, because Kestrel hosted fields keep the PAN off Harbourgate servers (AC-1); this does not remove every threat at this boundary, since a script on Harbourgate's own checkout page can still reach the hosted fields themselves, walked in the Kestrel connector's information disclosure row below | Public internet to Harbourgate's own service |
| 2 | Kiosk PIN pad to Kestrel, through the Kestrel terminal SDK (I-3) | Encrypted card-present data | Store-floor device to a provider-controlled channel Quay does not see the PAN inside; PIN pad encryption keys stay inside the pad's own tamper-resistant boundary and are injected and rotated by Kestrel, never held or transmitted by Harbourgate (section 3) |
| 3 | Quay to the Kestrel authorisation API, outbound (I-1) | Order value, tokenised card reference, OAuth 2.0 client credentials | Harbourgate to a PCI-scoped external processor, SLA N26 |
| 4 | Kestrel status webhooks, inbound (I-2) | Authorisation and capture outcomes, HMAC-signed | External processor to Harbourgate, signature verified before trust |
| 5 | Quay to the legacy Marlowe authorisation API, outbound (I-5), retiring | The card number itself, in transit through Harbourgate's own servers | Harbourgate to a second external processor; this is the boundary that keeps Harbourgate's own systems on this path inside its PCI DSS assessment scope (N55), not Marlowe, which is a processor and outside Harbourgate's own scope |
| 6 | Marlowe callback, inbound, legacy | Authorisation status, unsigned | External processor to Harbourgate with no signature to verify: F3 |
| 7 | Quay to the Tidewater wrapper, outbound (I-7), retiring | XML over HTTPS, client certificate expiring N66 | Harbourgate to the contractor's wrapper, itself a trust boundary the wrapper's own owner (Bea Lindqvist since R2 closed) cannot fully see inside |
| 8 | Settlement file SFTP, inbound, all three providers (I-4, I-6, I-8) | Daily and weekly settlement files, held on one shared drop across environments | External provider to Harbourgate storage; the drop is shared between pre-production and production, which is F2 |
| 9 | Routing flag, internal control plane | The routing flag (per-provider `[added 2026-05-21, D-017]`) that decides which provider a cohort's (`[added 2026-06-18, D-021]`) traffic reaches | Engineer to production traffic routing, gated by BR-007 |

## 3. Standing checks

- Secrets management: two kinds of secret, held differently. (a) Kestrel's OAuth 2.0 client credentials, the I-2 HMAC webhook-signing secret, Marlowe's legacy API key, Tidewater's client certificate, and every provider's SFTP key are held in the deployment secrets store, not in code or logs, readable only by the Quay service account, held by Bea Lindqvist; service credentials rotate on personnel change or suspected compromise (API contract section 3), the Tidewater certificate rotates only at expiry (N66) because no named process existed before Bea Lindqvist became caretaker (2026-04-24). Because Quay sits inside PCI DSS assessment scope (N55), requirement 8.6.3 also requires a periodic rotation interval on top of the event-triggered one; that interval is `[OPEN: not on the data sheet; owner Hamid Qureshi, to run the targeted risk analysis and set it, per API contract section 3, before the DEP-7 booking is committed (2026-11-20)]`. (b) PIN pad encryption keys are not in this store at all: they stay inside the PIN pad's own tamper-resistant boundary, injected and rotated by Kestrel under DEP-1's certification, and are never held or transmitted by Harbourgate.
- Least privilege: each provider integration runs under its own scoped service account (authorise, capture, void, refund for Kestrel; a single legacy scope each for Marlowe and Tidewater); scope reviewed quarterly by Hamid Qureshi
- Encryption in transit and at rest: TLS on outbound API calls and inbound webhooks (I-1, I-2); SSH, as SFTP, with per-provider keys on settlement-file transfers (I-4, I-6, I-8), which are not TLS. At rest: card tokens and masked PAN retained under the retention schedule (N58) in the deployment database, encrypted at rest by the platform's own disk-level encryption; key ownership `[OPEN: not named on the data sheet]`, never the full PAN. On the Kestrel path, the full PAN never reaches Quay at all (AC-1); on the Marlowe path, still live during the drain, the card number transits Harbourgate's own servers in flight (boundary row 5) until that leg retires.
- Audit logging: every decline carries provider, reason class and trace id into one event stream (AC-4); every provider flag change is logged with both approvers' names (AC-6, BR-007); alerts route to the payments on-call rotation
- Dependency and image scanning: [OPEN: specific scanner not named in the data sheet as of 2026-04-08; standard CI pipeline scan on every Quay deployment, blocking on high-severity findings, owner Tomasz Wierzbicki, tool name to be confirmed before Gate 4]
- Data classified per the data model: this journey does not fill a data-model.md; the data model referenced at N65 (section 6) sits outside this journey's sixteen filled artifacts, and the retention schedule that stands in for its section 5 is N58 (card token 13 months, masked PAN and expiry 13 months, cardholder name, billing address and email 7 years with the order, decline events 13 months, settlement files 7 years, wrapper log files deleted by 2027-01-15), and the legacy table shape's removal date sits in ADR-0002 (2027-03-31)
