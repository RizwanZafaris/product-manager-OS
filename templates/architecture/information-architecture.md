<!-- Information architecture is how a product is organised, labelled and
     navigated so people can find what is in it. Louis Rosenfeld and Peter
     Morville's Information Architecture for the World Wide Web (O'Reilly,
     1998) named the parts this file walks: organisation, labelling,
     navigation and search. It is a product decision: it settles what a user
     finds without help and what costs a support ticket.

     Card sorting has no single originator; it came into design from sorting
     tasks long used in psychology, and Donna Spencer's Card Sorting:
     Designing Usable Categories (Rosenfeld Media, 2009) is the standard
     practitioner reference. Tree testing has no single originator either;
     it is commonly traced to Donna Spencer's paper-based practice of asking
     people where in a text-only hierarchy they would look for something.

     The two answer different questions. A card sort shows how people group
     labels read out of context; a tree test shows whether they can find
     things in one specific hierarchy. A structure can match the card sort
     and still fail the tree test, because labels that group well do not
     tell a person which branch to open. Letting one stand in for the other
     is the most common error in this file. -->

## 4. Tree test

<!-- A tree test shows participants the hierarchy as plain text, with no
     visual design and no search, and asks where they would go to do a task.
     It measures structure and labels alone, which is its strength and its
     limit: a tree that passes can still fail on screen if the navigation
     pattern hides a branch. Before the run, list each task's correct
     destination, write each task without its destination's words, and date
     the pass rule. Test the old tree on the same tasks if one exists;
     without a baseline, "75% found it" has nothing to be better than.

     The arithmetic, per task, over the participants who attempted it:
     Success = participants who ended on a correct destination / attempted.
     Directness = participants who reached their final answer without moving
       back up the tree / attempted. It counts a participant who went
       straight to a wrong answer, so read it beside success, never alone.
       Tools define it slightly differently; write down which one yours uses.
     First click = participants whose first choice was the correct top-level
       branch / attempted.
     Interval: a 95% interval on success, because a small n makes a point
       estimate look firmer than it is. The adjusted Wald interval (Agresti
       and Coull, 1998, The American Statistician) works at small n:
       p' = (k + 1.92) / (n + 3.84), then p' plus or minus
       1.96 x sqrt(p' x (1 - p') / (n + 3.84)), clipped to 0 and 100%.
       For 7 of 10: p' = 8.92 / 13.84 = 0.645; the margin is
       1.96 x sqrt(0.645 x 0.355 / 13.84) = 0.252; the interval runs from
       39% to 90%. Seven of ten is not "70%" in any reading a decision
       should rest on. -->

## 9. How this file passes while the structure is wrong

| Failure | The tell | What to do |
|---|---|---|
| Org-chart navigation | Top-level labels are team names or internal product names | Rebuild the top level from section 1's tasks and section 3a's groups |
| Database-shaped tree | Categories mirror the tables, and labels are entity names | Read data-model.md as a constraint on storage, never as the menu |
| A card sort presented as proof of findability | The structure is called validated and section 4 is empty | Run the tree test; a card sort cannot show that anyone finds anything |
| Leading tree-test tasks | A task's text contains its destination's label | Rewrite the task from the words in support tickets or search logs |
| A percentage with no n | "82% found it" in a review deck | Write "k of n" with the interval, every time the number leaves the room |
| Testing only the tasks the new tree was built for | Every task passes and none of the old tree's failures was re-tested | Include the old tree's worst tasks and section 1's top tasks |
| Search as the fix for a failed task | "They can search for it" written against a failed row | Search is a second route, not a repair; record the fail and the synonym both |
| Renamed node breaks inbound links | Old URLs return not-found after launch and support macros go dead | Stable identifiers in paths, plus the redirect table with keep-until dates |
| Moving a habituated audience without a transition | Existing users' tickets rise after launch while new users do fine | Signpost moved items for a period, measure attempts on old paths, keep redirects |
