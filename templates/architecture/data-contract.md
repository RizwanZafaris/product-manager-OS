# Data Contract: [dataset or event stream name]

**Stage:** DESIGN (feeds [Gate 3: Architecture and risks reviewed](../../os/STAGE-GATES.md))
**Knowledge:** [Developer tools, APIs and platforms](../../knowledge/domains/devtools-api.md), whose adjacent-industries paragraph covers data platforms: a renamed column breaks jobs owned by people you never meet, and correctness fails silently; [role specializations](../../knowledge/roles/specializations.md), Data PM section, for who owns the datasets others build on
**Skill:** [spec-review](../../skills/spec-review/SKILL.md), run over the filled contract before Gate 3 so every service level and every check is written so that it can fail

**What checks this.** On the default path, where you fill this copy in an editor and a named human signs the gate form, Gate 3 is signed by the architect or senior engineer, the product owner and the security reviewer, per [os/STAGE-GATES.md](../../os/STAGE-GATES.md), and editing the document afterwards does not stale that signature: no hash binds it to the bytes. If you are running the optional `pmos` runtime, `python3 tools/init_product.py <product> --add` has already stamped this copy's artifact block from the frontmatter above, and approving Gate 3 with `pmos gate --bank-id design` records the copy's revision, so a later edit does stale that approval until the gate is proved again. Either way, no tool checks whether what you write is right; the people who sign the gate do. This paragraph is generated by `python3 tools/what_checks.py`.

Filled example: [Sorrelbank Market order lifecycle events](../../examples/sorrelbank-data-contract.md)

**When this is the wrong document.** Data that only the producing team reads: [data-model.md](data-model.md) is enough, and a contract with no consumer row is ceremony. A synchronous request and response interface: [api-contract.md](api-contract.md). Product events used only for the team's own dashboards: [analytics-instrumentation-spec.md](../delivery/analytics-instrumentation-spec.md), until a second team starts reading the stream, at which point it needs both. A one-off extract for a single analysis: a ticket.

<!-- A data contract is the promise a producing team makes to the teams that
     consume its dataset or event stream: what each record means, how fresh
     and complete it will be, how its quality is checked, who may see what,
     how it will change, and what happens when it breaks. The term has no
     single originator; it comes from data engineering practice, and this
     template takes the product side of it: who depends on this data, for
     which decision, and what they lose when it moves.

     It replaces neither neighbour. The data model is how the producer
     stores its own entities, and its PII classes are the ones section 3
     uses. The instrumentation spec is which events a product emits for its
     own metrics. The contract is for data that leaves the producing team.
     If the machine-readable form (a schema file in the producer's
     repository) and this file disagree, the schema file is what consumers'
     code runs against, so fix this file the same day. -->

## 10. How this contract passes while consumers still get hurt

| Failure | The tell | What to do |
|---|---|---|
| Schema without semantics | The Semantics column restates field names | Write unit, time zone, derivation and the meaning of null for every field |
| Silent change of meaning | A release note changes a definition while the field name and the MAJOR version stay | Count a change of meaning as breaking and bump MAJOR |
| Unlisted consumers | Access logs show readers who are not in section 2 | Run an access or lineage review before every breaking change, and add who you find |
| A service level with no measurement | "Data is fresh daily" with no indicator or query | Indicator, target, window, and the query name, per row |
| Checks that only alert | Nightly alerts in a channel with no named reader | Each check blocks publication or names the person who reads it |
| Notice nobody received | The policy lives in the producer's wiki and the consumers learned of the change from a broken job | Direct notice to named contacts, with acknowledgement counted in section 7 |
| Owner is a team | "Owner: data platform" | One named person, who can be asked why |
| Restatement without a flag | Corrected partitions overwrite old ones silently | A restated flag and a correction log consumers can read |
| Producer-only authorship | No consumer has read the contract before Gate 3 | At least one consumer signs below |
