## 9. How a rollout fails while looking controlled

| Failure | The tell | What to do |
|---|---|---|
| Thresholds set after the first reading | The "thresholds agreed on" date is later than the stage 0 start, or the halt numbers sit just above what stage 0 measured | Agree and date section 3 before stage 0; a threshold changed mid-ramp gets a stage-log row saying who changed it and why |
| Ramp by calendar | Stage log moves every Monday, and the readings column says "green" with no numbers | An advance row must show each guardrail's value and whether minimum volume was met |
| Ramp unit wrong for the product | A per-user percentage on a product sold per account; admins file tickets about colleagues who cannot see the feature | Ramp by account or tenant; the percentage counts accounts |
| Guardrail read at noise volume | Stage 2 cleared on a few dozen events, or halted on one bad hour | Minimum volume column; below it the reading is "not yet readable" and nothing advances |
| Everyone can halt, so nobody does | The halt column says "on-call" or "any engineer" | One name and one backup per guardrail, written before stage 0 |
| Kill switch that only works on the web | Tested in a browser; mobile clients cache flag values for a day | Section 1's cache lifetime is part of the kill-switch timing, and the test covers every client |
| Holdout dissolved one favour at a time | Holdout units released at customers' request until the holdout is below its sample size | The exception rule is written before GA, and released units leave the analysis rather than staying counted |
| The flag that never retires | A release flag older than its retirement date, still in code, with no debt-register row | Open the register row the day the flag is created; the date in section 7 is enforced by that row's review cadence |
