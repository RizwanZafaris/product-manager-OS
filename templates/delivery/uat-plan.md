**What checks this.** On the default path, where you fill this copy in an editor and a named human signs the gate form, Gate 5 is signed by the release owner, the product owner, the operations or support lead and the regulatory owner (regulated products only), per [os/STAGE-GATES.md](../../os/STAGE-GATES.md), and editing the document afterwards does not stale that signature: no hash binds it to the bytes. If you are running the optional `pmos` runtime, `python3 tools/init_product.py <product> --add` has already stamped this copy's artifact block from the frontmatter above, and approving Gate 5 with `pmos gate --bank-id deliver` records the copy's revision, so a later edit does stale that approval until the gate is proved again. Either way, no tool checks whether what you write is right; the people who sign the gate do. A copy of this one filled into a product workspace has a third, opt-in reader: `python3 lint.py --workspace products/<product>` refuses a copy that claims UAT is finished while a charter failed with no defect record and no approved exception, or whose charters were run against a build the sign-off does not name. It judges the contract, not the content. This paragraph is generated by `python3 tools/what_checks.py`.

Build repeats the candidate build above: a charter run against anything else is
a charter that has to be run again. Evidence is where the result can be seen.
Defect and Exception are "none" on a Pass, and both are required on a Fail.

Keep every charter in this one table. A row separated from its header by a
blank line or a sentence is no longer part of the table: markdown renders it as
text, and a check that reads the table does not see it. Group by cohort in the
Charter column rather than by splitting the table in two.

Keep the column names above. A check binds each column by its name: it accepts
the name used here and a short list of ordinary synonyms, it refuses the table
when two columns are both names it would accept, and it refuses the document
when no column carries a name it knows. A results column headed something it
cannot read is an error, not a pass. "Expected result" and "Done looks like"
are expectations and never the recorded result, so put the expected outcome in
"Done looks like", which is the column for it; a second column of Pass, Fail
and Blocked that disagrees with the result column is reported.

A second charter table is not a second hiding place. The check decides what a
charter table is from the table's own shape, not from the heading above it: a
table that carries four or more of the columns above under the names above, or
whose cells record Pass, Fail or Blocked, is read as a charter table wherever
it sits in the document, and refused if no column of it is named for the
result. What that cannot see is a table that does neither: fewer than four of
these columns, and results written as ticks or as "OK". Keep the charters
here.

## 5. Defect handling during UAT

<!-- UAT does not get its own severity scale. It used to, and the two scales
     disagreed: a job a tester could not finish was S1 here and S2 in QA, so the
     same defect blocked or did not block depending on which document the reader
     had open. The table below is a crosswalk, not a definition. -->

Severity is not redefined here. The canonical ladder is [testing strategy](testing-strategy.md) section 6, and the table below only maps UAT business wording onto those IDs.

| Canonical severity | What it looks like in UAT | Action inside the UAT window | Release rule (from the canonical ladder) |
|---|---|---|---|
| S1 | A tester loses work, or data or privacy is exposed, or the environment is unusable for everyone | UAT pauses, fix before resuming | Always blocks |
| S2 | A tester cannot complete a scoped job at all and there is no workaround | Fix inside the window, or the business sponsor accepts it in writing against the defect id | Blocks unless a named approver records who accepted it and why |
| S3 | A tester completes the scoped job only by working around the product, or a job outside the charter set is broken | Logged with a fix owner and date, UAT continues | Ships with a named fix owner and a fix date |
| S4 | Cosmetic friction that changes nothing about whether the job gets done | Logged, UAT continues | Ships, tracked |

## 6. Exit criteria and sign-off

UAT passes when:

- [ ] Every charter has run against the candidate build named at the top, and none is Blocked
- [ ] Every charter's Result is Pass, or that charter names a defect record and an approved exception in the register below whose retest result is recorded
- [ ] No open S1. No open S2 unless the business sponsor's written acceptance is attached to that defect id, and the same acceptance is the one the release-readiness known-issues row cites
- [ ] Testers answered "would you use this over the current way?" and the answers are recorded: [location]
