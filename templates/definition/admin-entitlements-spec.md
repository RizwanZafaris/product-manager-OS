## 9. How this spec fails

| Failure | The tell | What to do |
|---|---|---|
| Permissions enforced only in the interface | The matrix is filled, and a member's API token can still list every user | Every N cell has an API negative test in acceptance-criteria.md |
| Deprovisioning that leaves a way in | SCIM deactivation is "supported", and the deactivated user's API token still works | The deactivate row names sessions, tokens, shared links, and the seat, each with a latency |
| An audit log of the easy events | Sign-ins are logged; role changes, exports, and vendor access are not | Fill section 5 from the customer's security questionnaire, not from the events already emitted |
| Residency answered for the database only | Backups, logs, analytics copies, and support tooling are missing from section 7 | Every data class row filled, or an owner and a date in its last cell |
| Downgrade left undefined | No on-downgrade column, or "n/a" in every cell | Answer it per entitlement before Gate 2; the first downgrade will ask |
| Sales exceptions written as code | "SSO on Tier 2 for this one deal" shipped as a conditional on a plan name | Entitlements as per-tenant data with logged overrides; the request goes through [enterprise request triage](../../frameworks/prioritization/enterprise-request-triage.md) first |
| Enforced SSO with no way back in | No break-glass line, and an identity-provider outage is a support emergency | Break-glass accounts, held by the customer, logged and alerted on every use |
| Custom roles nobody can read | A tenant with many roles and no one able to say what a role grants | Roles are bundles of the section 2 permission rows, capped, and listed in the console with their rows |
