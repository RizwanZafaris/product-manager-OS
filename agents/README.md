# Agents: the role instruction files

This directory holds identities, not procedures. A file in [skills/](../skills/README.md) says how a piece of work is done, step by step. A file here says who is doing it: what that role may assert, what it must refuse, what it hands on, and the one hard rule that makes its output trustworthy. The distinction earns its keep at the boundaries. The drafting agent may fill a field; the validation agent may not, because a checker that edits becomes an author and then nobody is checking the author.

One role per run. A run that spans two roles loses the thing the separation was for. The router in [AGENTS.md](../AGENTS.md) names the five files and their hard rules; this page says what each one is for and who reaches for it.

| File | The role | Who invokes it |
|---|---|---|
| [research-agent.md](research-agent.md) | Gathers evidence for the DISCOVER set and marks everything it could not verify as an assumption. Its method is the product-analyst skill; this file is the constraints it runs that method under | A user asking for the facts behind a discovery template, or the Conductor handing off a research step from the DISCOVER bank |
| [drafting-agent.md](drafting-agent.md) | Fills exactly one named template per run from supplied evidence. Every field gets a traced value, an `N/A because <reason>`, or an open-field marker with an owner. It never invents a number or a name, and it flags conflicting evidence rather than choosing between sources | A user who has the evidence and wants the first complete draft, or the Conductor handing off template drafting once answers are accepted |
| [validation-agent.md](validation-agent.md) | Checks a draft against two references, the template it claims to instantiate and the gate it feeds, then walks the gate checklist line by line and reports what is missing, malformed, or unowned. It reports; it never rewrites | Before any draft reaches a human reviewer, and before any gate conversation starts |
| [red-team-agent.md](red-team-agent.md) | Attacks the artifact as three hostile readers in turn: the stakeholder hunting the weakest commitment, the auditor pulling the traceability thread, the attacker reading the spec as a map. For model-containing products it also runs the structured pass in [templates/ai/red-team-review.md](../templates/ai/red-team-review.md) | Before Gate 3 and Gate 5, or whenever a document has only ever been read by people who want it to succeed |
| [hermes-agent.md](hermes-agent.md) | The integration file for a Hermes-style self-hosted personal agent: a routing table that sends each Hermes task type to a tier in [routing/](../routing/README.md) and to the template that holds its output, plus the invariants a personal agent must keep (human approval before anything leaves, no invented claims, the approval queue and never the outbox) | A Hermes deployment doing product-management work, so its artifacts land in these templates and its model calls ride these tiers instead of a hardcoded model name |

The Conductor is deliberately not in this list. It is a skill, at [skills/conductor/SKILL.md](../skills/conductor/SKILL.md), because it is a procedure for running the loop rather than a role that produces one artifact. What it does with this directory is hand off: when a question bank routes to research, drafting, a premortem, a gap check, or a red team, the Conductor spawns that role with the accepted answers as its input, then treats what comes back as a draft rather than as evidence.

Two rules apply to every file here, from the gate rules in [AGENTS.md](../AGENTS.md). No role invents a number, a name, a citation, or a quote to make a field look finished, because a plausible fabrication is the one output this system exists to prevent. And no role signs a gate; it verifies and reports, and a named human in [os/STAGE-GATES.md](../os/STAGE-GATES.md) signs.
